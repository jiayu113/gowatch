# GoWatch AIOps 诊断层设计

状态:v1 定稿(2026-07-07) · 范围:设计文档 + 最小闭环 demo · 对应版本:v1.3.0

## 背景与动机

告警只回答 what,不回答 why。实际值守中,收到一条 `dns-broken` 或证书告警后,第一动作永远是手动拼上下文:翻这个目标最近的探测记录、看错误类型是偶发还是持续、对比延迟有没有先兆——这套动作平均要花 10-20 分钟,而且步骤高度模式化。模式化的人肉动作就应该被工程化。

本设计给 GoWatch 加一层**旁路的 LLM 根因诊断**:告警触发后,自动组装该目标的上下文(触发快照 + 历史统计),交给 LLM 生成"可能根因 + 下一步排查动作",落盘供人参考。

三个立场:

1. **旁路**:诊断层任何故障(超时、熔断、未配置)对告警主链路零影响。监控系统对 AI 层的依赖必须是"没有它照常活"。
2. **成本上界由设计保证**:三道闸门(冷却 / 日上限 / 熔断)让最坏情况下的调用量是一个算得出来的数,不是祈祷出来的。
3. **建议不执行**:输出只落日志与 JSONL,不触发任何动作。

## 目标与非目标

**目标(v1.3 范围)**
- 告警触发 → 自动生成一份结构化诊断(根因假设 / 排查动作 / 置信度)
- 三条降级路径全部经真实故障注入验证
- 成本三闸门 + 可观测(outcome 维度计数器)

**非目标(明确不做)**
- 自动执行任何修复动作——**永不做**,不进 backlog
- 诊断富化进 webhook body、Web 面板展示——留接口,进 backlog
- 多模型 fallback、RAG 知识库、流式输出、对话式追问——backlog

## 挂载点选型

| 候选 | 做法 | 结论与理由 |
|---|---|---|
| A. 包装 Notifier | 实现 `alert.Notifier` 接口,装饰 `WebhookNotifier` | ❌ 侵入 fire 路径;每条规则一个实例,冷却/熔断状态分散;LLM 延迟会占用 fire 的通知超时预算 |
| **B. emitCh 旁路订阅(入选)** | `main.go` 中 `emitCh` 消费者 fan-out:`SaveAlert` 照旧 + `analyzer.Submit(ev)` | ✅ emitCh 本来就是旁路持久化订阅点;Submit 非阻塞(满即丢);`internal/alert` 零改动;单点收敛,全局冷却/熔断/日上限好做 |
| C. 独立进程轮询 alerts 表 | 单独 binary 读 SQLite | ❌(当前)部署面 +1、诊断延迟高,demo 阶段过度设计。✅(演进)规模大了:诊断与监控故障域彻底隔离、独立伸缩 |

## 上下文设计:取什么、算什么、刻意不取什么

**取(全部白拿,不新增查询面):**
- `alert.Event` 本体:RuleName / Target / FireAt / Reason / **Snapshot**(触发时最近 N 次结果,evaluator 已附带)
- `store.GetByTarget(target, 50)`:该目标近 50 次历史

**算(三样统计,喂给 LLM 的"证据"):**
- 错误类型分桶:`{dns: N, timeout: M, ...}`——区分"单一故障模式"与"混合故障"
- 延迟分布:p50 / max——"挂之前有没有变慢"的先兆信号
- 故障时间线:本轮连续 down 的起点、已持续时长、窗口内 up/down 翻转次数(闪断 vs 硬故障)

**刻意不取:**
- 目标的 URL/超时等配置(不引 `internal/config` 包)。理由:少一个耦合面;target name 已语义化,对根因推理增量有限。若后续证明 URL 对诊断质量有实质提升,再以注入函数方式补,不直接 import。
- 跨目标关联(同一时刻别的目标也挂了吗)。这是好特性,但属于"事件关联分析",超出本版范围,进 backlog。

## 输出契约与 prompt 边界

要求 LLM 按固定结构输出 markdown,不解析为结构体(demo 不需要查询面,原文落 JSONL 即可):

```
## 可能根因(按可能性排序,每条附依据——依据必须引用上下文中的具体数据)
## 下一步排查(可直接复制的命令级动作,写明预期看到什么)
## 置信度说明
```

System prompt 写死三条边界:只提供排查建议、禁止任何"自动执行/已修复"类口吻;依据不足就明说不确定,不编造;总长受限、用中文。

## 降级金字塔(自上而下,每层都有"用户可见影响=零"的验证)

| 层 | 触发 | 行为 | 主链路影响 |
|---|---|---|---|
| 正常 | — | 出诊断,outcome=ok | 无 |
| 单次失败 | LLM 超时/报错/key 无效 | 记 outcome=error,日志一条 | 无(告警早已发出) |
| 熔断 | 连续 3 次失败 | 断路器开 5 分钟,期间 Submit 直接 suppressed | 无 |
| 满载 | Submit 时 buffer(16)已满 | 丢新保旧,outcome=dropped | 无 |
| 未启用 | aiops.yaml 不存在 / enabled=false | Analyzer 为 nil,main 一行 `if analyzer != nil` 兜底 | 无 |

buffer 丢新保旧的理由:诊断是增值服务,丢了不心疼;阻塞 emitCh 消费者才是事故(会拖住 SaveAlert)。

## 成本三闸门与测算

1. **冷却**:同 target+rule 10 分钟内只分析一次。与告警层 cooldown 不重复——那层防告警风暴,这层防"规则改配 / 多规则命中同目标"引发的成本风暴,层次不同。
2. **日上限**:默认 50 次/天,按天重置。
3. **熔断**:连续失败即停,失败重试本身也是成本。

上界测算:50 次/天 × 每次约 2K token(上下文 ~1.5K + 输出 ~0.5K),按 DeepSeek 价位为几分钱/天量级。

## 数据流

```
scheduler → evaluator.fire ──► WebhookNotifier(主链路,不变)
                └──► emitCh ──► SaveAlert(不变)
                          └──► analyzer.Submit ─(非阻塞)─► chan(16)
                                                              │
                              gate: 熔断开? 日上限? 冷却中? ──┤ suppressed
                                                              ▼
                            BuildContext(Snapshot + GetByTarget 50)
                                                              ▼
                                 LLM Complete(ctx, 15s timeout)─► 失败:onFail→熔断计数
                                                              ▼
                                 JSONL 落盘 + 日志 + outcome=ok
```

## 配置与密钥纪律

- `aiops.yaml`(gitignore,不进仓)/ `aiops.example.yaml`(占位,进仓)。文件不存在 = 功能禁用。
- **API key 只从环境变量读**(配置里只写变量名 `api_key_env`)。push 前 `grep -rn "sk-" .` 必须为空。
- LLM 接入走 OpenAI 兼容 `/chat/completions`:`base_url + model + api_key_env` 三个配置位。接口化(`LLM` interface)的两个收益:换模型改配置不改代码;单测可 mock。

## 落盘与观测

- 诊断落 `data/aiops/diagnosis-YYYYMMDD.jsonl`(追加写、按天切)。不进 SQLite 的理由:诊断是审计型数据,只有"追加 + 偶尔翻看"两个动作,没有查询面;JSONL 的运维成本趋近于零。
- 指标:`gowatch_aiops_analyses_total{outcome="ok|error|dropped|suppressed"}`——四个 outcome 对应金字塔四层,一条 PromQL 看清诊断层健康度。

## 边界立场:为什么"建议不执行"

1. LLM 存在幻觉,错误的建议 + 自动执行 = 把故障半径从"一个目标"放大到"执行动作波及的一切"。
2. 监控系统的公信力建立在"它说的都是真的"上;诊断层输出的是**假设**,假设与事实必须在产品形态上可区分(诊断带置信度声明、只落旁路文件)。
3. 自愈应该由确定性逻辑做(如 watchdog 的阈值重启),LLM 的位置在"帮人更快形成判断",不在执行链上。

## 自我思考

- **LLM 幻觉了怎么办?** 三层:建议不执行(错误建议无执行半径)→ 输出强制附依据与置信度(无依据的结论显形)→ 人是最终判断(产品定位如此)。
- **为什么不直接把诊断塞进 webhook?** demo 范围纪律;且通知渠道是消费方,不该被生产方(LLM 延迟 15s 级)阻塞。富化留 backlog,做也是"先落盘、通知带链接"的形态。
- **冷却和告警 cooldown 重复吗?** 不重复。告警 cooldown 防通知风暴(面向人);诊断冷却防成本风暴(面向账单)。规则改配、多规则命中同目标时,前者挡不住后者。
- **为什么 JSONL 不进 SQLite?** 见「落盘与观测」——没有查询面的数据不值得一张表。
- **etcd/集群模式下诊断会重复吗?** 不会。只有 leader 运行 scheduler → 只有 leader 的 evaluator 会 fire → emitCh 只在 leader 上有事件。follower 的 Analyzer 空转,代价为零。
- **上下文会不会泄漏敏感信息给 LLM 服务商?** 发出的内容 = 目标名 + 状态/延迟/错误类型统计,不含凭证、不含响应体。目标名已脱敏(demo 目标)。生产化前需过一遍数据出境评估——写进 backlog 与局限。
- **50 条历史够吗?** 对"单目标短期故障"够;对"缓慢劣化"(几天维度)不够。history_limit 可配,且这类分析更适合 backlog 里的独立进程形态。
- **LLM 服务商挂一天会怎样?** 熔断反复开合,outcome=error/suppressed 计数上涨,告警与监控完全正常——这正是旁路设计要买的东西。

## backlog 与演进

1. 独立进程化(挂载点候选 C):诊断与监控故障域隔离,规模化方向
2. webhook 富化(通知带诊断链接)/ `/api/aiops/recent` 只读端点 / Web 面板
3. 跨目标事件关联(同窗口多目标故障的共因分析)
4. 数据出境与脱敏策略(生产化前置)
5. 多模型 fallback / 本地小模型兜底
